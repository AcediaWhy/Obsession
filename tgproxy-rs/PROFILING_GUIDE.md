# Obsession Telegram Proxy (obsession-tg-proxy)

## 📌 Что такое obsession-tg-proxy?

Это Rust-реализация Telegram-прокси, которая:
- Заменяет старый Python-бинарник `TgWsProxy`
- Работает как headless MTProto<->WebSocket мост
- Интегрирован в защищённый рантайм Obsession (WinDivert/winws)
- Поддерживает fallback через Cloudflare-relay

## 🔍 Что будем профилировать?

Основные компоненты:
1. **`main.rs`** — точка входа, обработка CLI-аргументов, запуск Tokio runtime
2. **`bridge.rs`** — обработка клиентских соединений, обфускация, маршрутизация
3. **`cfrelay.rs`** — fallback через Cloudflare-relay
4. **`crypto.rs`** — шифрование/дешифрование MTProto
5. **`upstream.rs`** — работа с Telegram DC (TCP/WebSocket)
6. **`ws.rs`** — WebSocket-клиент для подключения к Telegram
7. **`fake_tls.rs`** — FakeTLS-слой для маскировки трафика

## 📊 Что мы хотим узнать?

1. **Где тратится больше всего CPU?**
   - Обработка пакетов?
   - Шифрование/дешифрование?
   - Сетевые операции?

2. **Есть ли утечки памяти?**
   - Если да, то где аллоцируются большие буферы?

3. **Какие функции вызываются чаще всего?**
   - Например, `read_client_init`, `run_session`, `bridge_ws_reencrypt`

4. **Есть ли блокирующие операции?**
   - Например, долгие TCP-connect, DNS-запросы

## 🛠️ Как профилировать?

### Вариант 1: Flamegraph (рекомендуется)
```bash
# 1. Соберите бинарник с отладочной информацией
CARGO_PROFILE_RELEASE_DEBUG=true cargo build --release

# 2. Запустите профилирование
cargo flamegraph --bin obsession-tg-proxy -- --port 1443 --secret 12345678901234567890123456789012

# 3. Откройте flamegraph.svg в браузере
```

### Вариант 2: Вручную с perf (Linux) или dtrace (macOS)
```bash
# На Linux:
perf record -g -- ./target/release/obsession-tg-proxy --port 1443 --secret ...
perf script | stackcollapse-perf.pl | flamegraph.pl > flamegraph.svg
```

### Вариант 3: Профилирование памяти (heaptrack)
```bash
# Установите heaptrack
sudo apt-get install heaptrack heaptrack-gui  # Linux

# Профилируйте
heaptrack ./target/release/obsession-tg-proxy --port 1443 --secret ...
heaptrack_gui heaptrack.obsession-tg-proxy.*.heap
```

## 📈 Что анализировать в flamegraph?

1. **Ширина блока** = время выполнения функции
   - Широкий блок = горячая функция
   - Узкий блок = мало времени

2. **Высота блока** = стек вызовов
   - Глубокий стек = много вложенных вызовов
   - Плоский стек = мало вложенности

3. **Цвет** = не важен (детерминированный)

4. **Топ-5 функций** — обычно это:
   - `tokio::runtime::task::waker` (планировщик задач)
   - `tokio::net::tcp::TcpStream::read` (чтение из сокета)
   - `aes::block_decrypt` (дешифрование)
   - `serde_json::from_slice` (десериализация)
   - `tokio::time::sleep` (ожидание)

## 🚀 Пример анализа

Если flamegraph показывает:
- Широкий блок `bridge::handle_client` → значит, основное время уходит на обработку клиентских соединений
- Широкий блок `crypto::decrypt` → значит, шифрование/дешифрование занимает много времени
- Много узких блоков `tokio::task::spawn` → значит, много мелких задач

## 🔧 Возможные оптимизации

1. **Если много времени уходит на шифрование** →
   - Использовать SIMD-инструкции (если не используются)
   - Уменьшить размер ключей (но это небезопасно)
   - Кешировать сессионные ключи

2. **Если много времени уходит на чтение/запись** →
   - Увеличить буферы (сейчас 65536 байт)
   - Использовать zero-copy парсинг
   - Перейти на async I/O с буферизацией

3. **Если много времени уходит на планировщик задач** →
   - Уменьшить количество spawn'ов
   - Использовать пул потоков фиксированного размера
   - Перейти на более лёгкий рантайм (например, `monoio`)

4. **Если есть утечки памяти** →
   - Использовать `Arc<Mutex<T>>` вместо `Box<T>`
   - Убедиться, что все `JoinSet` и `tokio::spawn` завершаются
   - Проверить, что буферы не накапливаются в `MsgSplitter`
