# Первый этап переработки локального подбора Zapret2

Дата: 2026-10-02. Policy: `adaptive_owned_flow_programs_v9`. Встроенный pack: `0.9.0`.

Цель этого этапа — связать результат HTTPS-проверки, наблюдение TCP и исполнение программы с одним соединением. Это необходимая основа последующего синтеза, а не обещание универсального обхода. Внешние серверы и VPN не используются. Движок остаётся Zapret2.

## Исполнение программы

Защищённая служба загружает проверенный по SHA-256 `obsession-executor.lua` для диагностических adaptive TLS-профилей. Исполнитель компилирует допустимые операторы через штатные Lua helpers Zapret2 и фиксирует неизменяемую программу в состоянии отслеживаемого соединения. Максимум — 16 шагов. Обработка следующего пакета существующего соединения не подменяет его программу новым профилем.

Исходная пара адресов/портов записывается до изменений пакета. Receipts содержат программу, профиль, PID процесса, serial соединения, направление, тип payload, количество вызовов операторов и результаты send API. Ошибки Lua сохраняются с той же привязкой. Обёртки сохраняют return values, включая nil, и исходные ошибки штатных функций.

Обычные встроенные профили и QUIC продолжают использовать прежний путь. Hot-update без перезапуска процесса в этот этап не входит: смена кандидата всё ещё выполняется защищённой заменой runtime.

## Проверка в том же сокете

Основные обычные TLS-пробы выполняют TCP connect, TLS handshake и HTTP/1.1 request через один принадлежащий проверке сокет. Измерение содержит его local/remote tuple и точную стадию отказа. Используются DNS-адреса текущей сессии, проверка сертификата и ограниченный deadline. TLS resumption отключён. Чтение HTTP ограничено по заголовкам, body, chunks и trailers; неоднозначные или обрезанные сообщения отклоняются.

Discord API/gateway требуют полного ожидаемого JSON-ответа. `/app` пока использует отдельную существующую проверку HTML и JS asset; дополнительная TLS-проба помечается `supplementary_tls`. Успех API или дополнительного handshake не подменяет успех обязательного запроса `/app`.

Это не воспроизведение fingerprint приложения Discord. Вход в приложение, WSS-сессия, голос и CDN в этом этапе не подтверждаются.

## Выбор следующего эксперимента

Решения принимаются по основной HTTPS-пробе и receipts именно её программы/сокета/поколения. Смешанные PID, serial, профили, поколения и неоднозначные tuples не подтверждают исполнение.

| Наблюдение | Решение |
| --- | --- |
| Ошибка текущего executor/send API или выход движка | Остановить TLS-подбор после проверенного восстановления; исследовать исполнение |
| Повторяющийся отказ TCP connect | Исследовать TCP-путь |
| Ошибка проверки TLS-сертификата | Исследовать TLS peer |
| TLS работает, обязательный HTTP-ответ не проходит | Исследовать прикладной ответ |
| Нужная программа исполнилась, полный ClientHello наблюдается, ACK-прогресса нет при полном capture | Проверить порядок/структуру сегментации |
| На том же отказавшем TLS-соединении есть ACK-прогресс или ServerHello | Проверить точки разбиения TLS |
| Исполнение программы не подтверждено | Запросить измерение; после двух таких попыток остановиться после возврата |

Для изменения порядка/точек разбиения формируется максимум два контрольных варианта на одну исходную программу и решение. Проверенные эквиваленты не добавляются повторно; совпавший непроверенный вариант получает приоритет. Общий deadline поиска сохраняется, добавление контролей его не продлевает.

История и оценка подтверждённой стратегии не ухудшаются из-за неустановленного исполнения, ошибки запуска, TCP-пути или сертификата. События старой попытки/сессии/поколения не влияют на текущую. Успешный HTTP-quorum не позволяет сохранить кандидата, если текущий движок уже завершился или executor сообщил ошибку.

## Пределы наблюдения

Вызов оператора не доказывает, что он преобразовал пакет. Успех send API не доказывает доставку на физический интерфейс. ACK или ServerHello не подтверждает HTTP. Отсутствие ACK используется только при полном packet capture, наблюдённом SYN/ACK и ClientHello, известном ACK-offset и отсутствии конфликтов/потерь датчика.

Каждый из двух Lua-источников (observer и executor) ограничен 512 событиями и 120 секундами. Служба сохраняет максимум 128 строк / 16 KiB. Общим сообщениям старого observer отведено максимум 32 строки / 4 KiB; при переполнении сохраняются последние flow receipts и явно отмечается truncation. Потеря ранней строки latch не уничтожает положительное подтверждение из валидного packet receipt, но не восстанавливает отсутствующие факты. Ограничения packet observer: 300 секунд, 128 tracked flows, 32 reported flows, 16 KiB stream prefix. Физический порядок пакетов и lifetime TCP tuple без собственного ISN/time anchor остаются неопределёнными.
