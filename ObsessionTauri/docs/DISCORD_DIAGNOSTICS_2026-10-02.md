## Что объясняет расхождение, а что остаётся гипотезой

Сохранённый Discord/TLS конфиг до и после обоих тестов одинаков:
`multidisorder:pos=1,2,midsld,sniext`, `out_range=-d10`. Возврат создаёт новый
процесс. До/после дневного теста использован один SessionDnsCache, поэтому
смена DNS-адреса внутри этого теста не объясняет восстановление доступа.
Одной короткой успешной серии после отката недостаточно, чтобы установить
причину: это может быть состояние runtime/соединений или изменение
сетевых условий за время теста. Нужен отдельный контроль перезапуска того же
конфига с повторными измерениями до изменения стратегии.

`app.log` уточняет важную границу этой гипотезы: при открытии приложения в
12:57:25 DPI был выключен; пользователь запустил его через интерфейс в
12:57:28, служба сообщила успех в 12:57:29. Первая проверка началась в
12:57:35. Это свежий запуск, а не процесс, непрерывно работавший с ночи.
Снимок поколения ночного финала — `1790869840863852`, дневного начала —
`1790869840863853`. Долгая жизнь процесса не установлена как причина.

Между ночным и дневным тестами адреса различались:

- Ночь: discord.com `162.159.137.232`, gateway `162.159.136.234`.
- День: discord.com `162.159.138.232`, gateway `162.159.134.234`.

Это различие условий, а не доказанный корень проблемы. Ночной результат
доказывает измеренное восстановление проверяемых целей в той сессии; он не
доказывает стабильную работу клиента на других адресах.

«Проверить подбор с нуля» исключает точный исходный fingerprint намеренно.
Он проверяет новый вариант и всегда возвращает исходный, включая успех.
Подставлять восстановленный исходный конфиг как успешный новый кандидат нельзя.

Нынешний gateway probe — HTTPS GET `/` с завершённым телом и допустимым 404.
Он не устанавливает WebSocket. HTML/JS probe не исполняет клиент в браузере.
Официальный [Discord Gateway](https://docs.discord.com/developers/events/gateway)
описывает WSS-подключение и событие Hello с opcode 10 перед авторизацией.
Проверка WSS/Hello нужна для более сильного подтверждения; авторизация, CDN и
голос также не измеряются нынешним TLS-тестом.

## Найденный дефект обратной связи

`runtime.rs` передаёт свежий дополнительный TLS stage планировщику отдельно
от результата основного HTTPS-запроса. Планировщик допускает обучение по
`request_timeout` только при текущем измеренном TLS fault. Но
`ExperimentDesign::observe` разрешал контроль удаления остальных шагов
составной стратегии только при основном `failure_stage=tls` и только для
MultiSplit/MultiDisorder. Поэтому сегодняшние наблюдения с основным
`request_timeout` и измеренным `tls_timeout` не запускали такой контроль.

Четыре фактических составных кандидата (попытки 5, 7, 9, 11), их id и
измерения сохранены в
`src-tauri/src/adaptive_strategy/fixtures/discord-20261002-tls-feedback.json`.
Регрессия воспроизводится через настоящий планировщик с оставшимися seeds.
Контроль должен сохранить аргументы конечного преобразования сегментов,
убрать предыдущие fake/clone, пройти обычную валидацию и быть проверен раньше
следующего независимого рецепта. Сам по себе он не означает восстановление.

Исправление v8 передаёт текущий измеренный TLS stage в дизайн эксперимента
отдельно от основного результата. При request_timeout + текущем TLS fault
проверяется конечный MultiSplit/MultiDisorder/FakeDSplit/FakeDDisorder/
HostFakeSplit без предшествующих шагов, если нет повторяемого частичного
HTTPS-успеха. Такой контроль имеет приоритет перед очередным независимым
рецептом. Он не возобновляется для точного уже проверенного/исключённого
конфига и проходит обычный admission по оставшемуся бюджету 90 секунд.
Отсутствующий/устаревший stage, успешный дополнительный handshake, ошибка
DNS/TCP или сертификата не разрешают вывод о TLS-отказе из opaque timeout.

В отчёт добавлен `baseline_became_healthy_after_restart`, а в видимый журнал —
сообщение о расхождении проверки исходного конфига до/после. Это не меняет
итог проваленного подбора на успех и не устанавливает причину восстановления.

Следующие неизвестные: причина изменения доступа исходного runtime, эффект
пакетов после принятия API отправки и реальная устойчивость клиента. Эти
вопросы нельзя закрыть ростом числа рецептов или успешным parser-only тестом.

- Провести 3–5 близких по времени пар A/B. Порядок внутри пары заранее

### Реализованная проверка повторяемости, 2 октября

В Discord/TLS добавлена кнопка **«Проверить повторяемость»**. Запуск требует
отметить выключенный VPN. Режим выполняет холодный подбор без истории,
затем сравнивает точный подтверждённый кандидат с passthrough в 3 парах.
Хотя бы одна пара имеет порядок AB, хотя бы одна — BA; третья и порядок
пар случайны и заранее записываются. Обе стороны каждого блока проходят
защищённый stop/start, включая соседние блоки с одинаковым вариантом.

На сравнение выделены отдельные 120 секунд. Поиск сохраняет свой бюджет
20/30/90 секунд. Защищённый replace и окончательный rollback не обрываются
посередине транзакции из-за истечения времени или отмены.

Из заранее подготовленного системным resolver набора выбирается один IP
на authority (предпочтение IPv4), отдельный cache фиксирует его на все
6 блоков. Исходный cache сохраняется для финальной проверки исходного
конфига. В каждом блоке — 2 новых раунда по 3 секунды на цель:
API с проверкой JSON, gateway HTTPS, HTML /app плюс один JavaScript asset.
Reqwest client создаётся заново на каждую цель каждого раунда, proxy выключен.
Одновременно проверяются посторонние HTTPS-цели. Настройки DNS не меняются.

Снимки активных маршрутов IPv4/IPv6, интерфейсов, link state и метрик
снимаются до сравнения и до/после каждого блока. Смена или недоступность
снимка запрещает положительный вывод. Это контроль неизменности маршрута,
а не автоматическое удостоверение отсутствия всех видов VPN/proxy.

`confirmed_effect` допустим только при полном наборе 6 блоков, разных
принадлежащих сессии поколениях и обоих порядках пар: с кандидатом все
3 цели проходят каждый раунд; без обхода каждый раунд не проходит хотя бы
одна цель; DNS работает, хотя бы один общий HTTPS-контроль отвечает,
маршруты не меняются. До и после каждого блока защищённая служба
подтверждает живые процессы движка с тем же поколением и включённой
диагностикой; падение процесса не может считаться отказом здорового
контроля. Любой сбой кандидата при корректных предусловиях —
`not_reproduced`. Успешный раунд контроля, смена маршрута, сбой DNS/общей
сети, неполная проверка или истёкший бюджет — `inconclusive`.

Прогресс и итог записываются как `effect_validation_plan`,
`effect_validation_routes`, `effect_validation_block`,
`effect_validation_finished`. Состояние процесса и ограниченный observer
сохранены в `effect_validation_runtime`. В `benchmark_restoration` и `finished` сохранён
тот же receipt. Итоговый UI `effect_confirmed` появляется лишь после
подтверждённого возврата точного исходного snapshot без диагностического
observer. Отмена ждёт завершения владеющего транзакцией worker. При чужом
поколении возврат не перезаписывает чужую конфигурацию, итог сообщает ошибку.
Кандидат этого теста не сохраняется в рекомендациях или истории.

Сетевой эффект нового режима ещё не измерен: VPN/runtime пользователя
в ходе разработки не переключались. WSS/Hello, browser execution и голос
остаются вне этого HTTPS-теста. Устойчивость через 10–15 минут и после
смены адресов также потребует отдельных измерений. Три пары не дают
процента надёжности и не доказывают оптимальность поиска.

### Офлайн-проверка решения по дневным ошибкам

`DISCORD_PLANNER_REPLAY_2026-10-02.json` создан выполнением регрессии на
четырёх реальных дневных receipts (попытки 5, 7, 9, 11). На каждом таком
decision point текущий `request_timeout` вместе со свежим `tls_timeout`
вызывает контроль с удалением ведущих clone/fake и сохранением последнего
преобразования сегментов. В результате следующими проверяются соответственно
`fakedsplit`, `multisplit`, `multidisorder`, `fakeddisorder` с теми же аргументами,
раньше очередного непроверенного рецепта.

Это повтор решений при заданных наблюдениях. Воспроизведение не исполняет
сетевые кандидаты и не утверждает, что они работают. Регрессии отдельно

## Найденный дефект наблюдения и исправление диагностики

В production путь запуска проходит через `protected_runtime::dpi_start`
и `ProtectedDpiBackend`. Старый app-owned `start_zapret2_eyes` туда
не подключён. Service-owned `LegacyObserverRuntime` запускается только
при `legacy_reliability`, а этот параметр запрещён для Zapret2.
Таким образом, нули Eyes в адаптивных отчётах не были измерением
отсутствия Reset/Blackhole/Working. Этот канал не получал пакеты.
Lua observer — отдельный механизм; его `ready` не доказывает запуск Eyes.

Добавлен независимый `PacketObserver` внутри защищённой службы:

* Запускается только при диагностическом флаге Zapret2, после запуска
  движка и до проб. DLL берётся из проверенного Zapret2 catalog и
  повторно проверяется. Произвольных путей или capture-фильтров в IPC нет.
* Использует существующий WinDivert capture с `SNIFF | RECV_ONLY | NO_INSTALL`.
  Семантика сверена с [первичной документацией WinDivert](https://reqrypt.org/windivert-doc.html#divert_open):
  sniff копирует пакет, receive-only запрещает инъекцию, no-install
  требует уже установленного драйвера.
  Фильтр включает TCP/443 с чистыми ACK; настройки перехвата winws2
  не меняются. Legacy Manager, автоматическое восстановление и режимы
  Legacy не запускаются.
* Для каждого runtime generation отдельны таблица, counters и handle.
  При смене, возврате и остановке sensor закрывается; незавершённый
  teardown запрещает следующий capture. Ошибка старта не ломает движок,
  но становится явным `startupFailed` с ограниченным сообщением.
  Автоматический предел — 300 секунд на поколение; завершение движка
  также останавливает наблюдение.
* Таблица ограничена 128 потоками, IPC — 32 потоками. Первые TLS-записи
  собираются в RAM с пределом 16 KiB на направление и привязкой к SYN.
  Выводятся только потоки с распознанным SNI из фиксированного набора
  диагностических целей. Payload, SNI и абсолютные TCP seq/ack в IPC
  и отчёт не попадают.
* Отчёт показывает SYN-ACK, размер распознанного ClientHello, продвижение
  входящего ACK, количество пакетов с повторным seq, входящие данные,
  RST/FIN, распознанные ServerHello/Alert и конфликт перекрывающихся
  сегментов. Повтор seq может возникнуть от преобразования или injection:
  он не называется доказанной ретрансляцией ОС.
* Дополнительная TCP/TLS-проба теперь сохраняет локальный адрес сокета.
  `packet_probe_correlation` сопоставляет оба адреса, а не только IP/SNI.
  Наблюдение чужого сокета не становится доказательством этой пробы.
  Потери очереди, parse errors, eviction, ошибка worker или неизвестное
  состояние запрещают отрицательный вывод по отсутствию ответа.

Захват выполняется на network layer с priority 0. Порядок относительно
обработчика winws2 и физическая доставка пакетов не подтверждены. Эти
метаданные помогают разделить наблюдаемые стадии, но не устанавливают
виновника и не заменяют HTTPS-проверку. Составные преобразования могут
делать распознавание префикса неоднозначным; тогда отчёт показывает
конфликт или отсутствие точного потока, а не придумывает диагноз.

Пакетные метаданные пока сохраняются для диагностики, **не используются
как автоматическое доказательство успешного кандидата**. Нынешний planner
остаётся эвристическим портфелем с компонентными контролями, а не обученной
моделью сети. Его дальнейшие правила следует менять по конкретному
packet receipt, не приписывая этому изменению уже доказанное восстановление.

Проверено: 216 adaptive tests (2 внешних integration tests исключены),
82 Eyes tests, 203 tests службы (3 внешних/драйверных исключены),
32 protocol tests. Named-pipe tests службы отдельно прошли вне песочницы.
Сетевой эффект нового наблюдателя на пользовательской сети ещё не измерен.

Корень ложного впечатления от итогового предупреждения — дефект нашей

второго раунда; здорового контроля в этих отчётах не было.

но сохраняет оба раунда и после первого неуспеха. Ошибка DNS по-прежнему
прерывает измерение и делает его неопределённым. Порог доказательства не
снижен. Дополнительно проверяются номера раундов и кворум 2 из 2; в отчёт
попадает конкретная причина, а в журнал — число реально собранных раундов.
