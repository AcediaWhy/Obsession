# Discord Gateway: обязательная проверка WSS — 2026-10-03

Причина изменения: ночное и утреннее парные сравнения оба подтвердили HTTPS, но реальный клиент утром устанавливал Gateway за 17,7 секунды. Отказ контрольного блока без обхода пользователь воспринимал как отказ конфига. HTTPS GET к Gateway не проверял WebSocket.

## Что реализовано

В TLS-подборе Discord обязательная цель Gateway теперь использует `wss://gateway.discord.gg/?v=10&encoding=json`. Для успешного раунда требуются:

1. Новое TCP-соединение к подготовленному системным DNS адресу, проверенный сертификат и новое TLS-рукопожатие без resumption.
2. Корректный HTTP Upgrade, сообщение HELLO (`op=10`) с допустимым целочисленным `heartbeat_interval`.
3. WebSocket ping со случайными 16 байтами и pong с точно таким же содержимым.
4. Закрытие пробного соединения и вторая такая же проверка на новом сокете к тому же успешному IP.

HELLO должен поступить не позднее 2000 мс от начала соединения, pong — за 750 мс. Это заданные требования к задержке приложения, а не диагноз ТСПУ. Оба соединения и перебор адресов делят прежний дедлайн цели: 3 секунды при screening/парном сравнении; общий бюджет поиска не увеличен. Альтернативные системные адреса запускаются с интервалом 200 мс, чтобы исправный первый адрес не создавал сразу восемь WSS-соединений. Остальные попытки отменяются при успехе и отмене измерения.

В отчёт попадают этапы каждого из двух соединений: TCP, длительность TLS и Upgrade, время до HELLO, RTT pong, объявленный heartbeat interval, успешность и конкретный этап отказа. TCP tuples принадлежат тем же сокетам, которые несли WSS, с отдельным scope `primary_gateway`. HTTP 101 сам по себе успехом не считается. Сырой ответ, cookies, данные аккаунта и токены не сохраняются; Identify не отправляется.

`gateway` и `gateway_latency` отделяют отказ после успешного TLS от TLS-отказа. Они не ухудшают TLS-историю и не учат портфель TLS как отрицательному результату механизма. Если TLS на принадлежащем Gateway сокете действительно не проходит, его native receipts могут направить следующий TLS-эксперимент, даже когда HTTPS API уже отвечает.

Повторное подтверждение, сохранение кандидата и парное сравнение используют новый полный quorum. Старые HTTP-only флаги без Gateway evidence не удовлетворяют обязательной WSS-цели. Политика `discord_gateway_hello_pong_fresh_reconnect_v1` включена в fingerprint области Discord: прежнее HTTP-only подтверждение/история не подменяет новое. Другие категории и установленный движок этими изменениями не мигрируются.

## Интерфейс

На каждом блоке сравнения отображается, что проверяется сейчас: найденный конфиг или контроль без обхода. На контрольной калибровке также показан контроль, а не исходный конфиг. Кратко поясняется, что отказ контроля не является отказом исходного/найденного конфига. В свёрнутых технических деталях Gateway помечен WSS; видны времена HELLO первой и второй попытки. Длинные инструкции в основную карточку не возвращались.

## Проверки

- Локальный TLS/WebSocket сервер: два разных исходящих порта, exact tuples и отсутствие credentials; отказ Upgrade, неверный opcode, слишком большое сообщение, отсутствие HELLO, неправильный pong, отказ второго соединения, медленный HELLO, неверный сертификат, освобождение сокетов при отмене.
- Обязательный quorum не подтверждается HTTP-only флагами, единичным WSS-успехом или неполной Gateway evidence.
- Парное сравнение не объявляет эффект, если в любом раунде кандидата отсутствует подтверждение WSS.

## Границы проверки

Эта проверка измеряет доступность Gateway до авторизации, двустороннюю отзывчивость и повторное новое соединение. WebSocket pong — не Discord Heartbeat ACK. Она не делает Identify/READY или authenticated Resume, не ждёт полный heartbeat interval, не проверяет региональный `resume_gateway_url`, голос, полное выполнение Discord UI или доступность всю ночь. Проверка использует Rustls ClientHello; его форма отличается от Chromium/Electron. Успех синтетической WSS-пробы не доказывает устранение задержки настоящего клиента.

Региональный хост из лога не сделан универсальной обязательной целью: он относится к прошлой авторизованной сессии, а его утренний reconnect был уже после остановки DPI. Нельзя смешивать эти условия или закреплять один регион для всех пользователей.

Установщик не запускается автоматически. Для новой проверки установить Gateway-сборку, отключить VPN и запустить «Начать измерение» в Discord/TLS; обычный подбор может сохранить подтверждённый вариант. «Подбор с нуля» и сравнения остаются диагностическими: после них возвращается исходный конфиг, найденный вариант не применяется навсегда. Проверить также скорость открытия самого Discord. Старые зафиксированные сравнения другой сборки отклоняются; новый anchor можно создать после полного нового теста.

Сетевой успех новой сборки и ускорение настоящего Discord пока не подтверждены. Это реализация следующего этапа измерения и отбора, не завершение всей системы адаптации.

## Первичные источники

- [Discord Gateway: подключение и HELLO](https://docs.discord.com/developers/events/gateway#connecting) — проверено через Firecrawl 2026-10-03. Документация не дала явного подтверждения обмена Discord heartbeat ACK до Identify; поэтому вместо этого используется стандартный WebSocket ping/pong.
- [RFC 6455, Ping/Pong](https://www.rfc-editor.org/rfc/rfc6455.html#section-5.5.2) — pong должен повторять содержимое ping, client frames маскируются.
- [tokio-tungstenite 0.28: WebSocket на существующем сокете](https://docs.rs/tokio-tungstenite/0.28.0/tokio_tungstenite/fn.client_async_with_config.html) — применяется поверх принадлежащего проверке TLS-сокета; handshake, masking и frames разбирает библиотека.
