# Переработка стратегий Zapret2 — 28 сентября 2026

## Что изменилось

Генератор TLS для Discord, YouTube/Twitch и Gaming перебирает до 12 кандидатов.
Сначала идут разрезание и перестановка, затем статический fake, клонированный
ClientHello, `hostfakesplit`, `fakedsplit`, `fakeddisorder` и варианты с TTL.
Вариант, зависящий только от TCP timestamps, находится в конце списка.
Подтверждённый для сети кандидат сохраняет приоритет. Уже проверенные кандидаты,
текущая стратегия и базовый профиль исключаются по отпечатку команды.

- В fake-разрезаниях `pattern` задаёт поддельные части. `blob` запрещён,
  поскольку он заменял бы исходный запрос. `pos` принимает одну позицию.
- Клон хранится в локальном `adaptive_tls_clone`. Первый шаг заменяет SNI
  на `www.google.com`, второй отправляет клон через `fake`. При невозможности
  клонирования используется `tls_google`. Проверяются порядок шагов, наличие
  механизма отбрасывания fake и отсутствие подмены глобальных блобов.
- TTL-кандидаты используют отдельные ограничения IPv4 и IPv6, сейчас по 5.
  Их пригодность зависит от маршрута и положения DPI.
- Приложение и IPC-протокол службы проверяют одинаковые ограничения.
  Служба компилирует новые типизированные функции самостоятельно.
- Базовые TLS/QUIC-профили генератора приведены в соответствие с манифестом.
  Регрессионный тест сверяет правила и диапазон пакетов с реальным пакетом.
- В записи `candidate_start` журнала добавлено поле `family`.

## Голос Discord

Пакет `builtin.base` обновлён до `0.8.0`. Голосовые профили сохраняют прежние
порты и фильтры Discord discovery/STUN. Четыре уровня теперь проверяют:

1. Нулевой fake, 6 повторов — прежний базовый вариант.
2. IP-фрагментацию по границе 8 байт и удаление исходного пакета.
3. Нулевой fake, 2 повтора, затем такую же фрагментацию.
4. Нулевой fake с TTL/HL 5, 2 повтора.

Это экспериментальные варианты для ручной проверки RTC. Успех TLS-подбора
подтверждает только проверяемые API/gateway; статус голоса остаётся
«не проверен». Автоподбор не выбирает голосовой профиль по HTTPS-результату.

## Проверка и применение

Проверки приложения охватывают старые ошибочные параметры, локальность и
порядок клонирования, ограничения новых аргументов, отсутствие дублей и
передачу всех генерируемых кандидатов через IPC. У протокола есть отдельные
отрицательные тесты на некорректные запросы.

`npm run verify:dpi-parsers` собирает службу и проверяет команды поставляемыми
движками с `--dry-run`. В проверку включены восемь форм адаптивных TLS-правил
для каждой категории и уровня. Этот режим проверяет CLI и наличие ресурсов;
он не исполняет Lua и не доказывает работоспособность обхода.

Для применения нужны обновлённые приложение, служба и пакет ресурсов.
Работоспособность на Дом.ру, устойчивость подключения и голос проверяются
на реальной сети после установки. Обычный успешный HTTPS-запрос не служит
подтверждением исправленного RTC.

Результаты локальной проверки:

- Приложение: 740 тестов прошли, 2 пропущены.
- Протокол: 20 тестов прошли.
- Служба: 171 тест прошёл, 2 пропущены. Четыре теста именованных каналов
  первоначально получили отказ Windows в песочнице и прошли вне неё.
- Проверка пакета: 380 запусков с `--dry-run` прошли, включая 224 составных
  Legacy-плана и новые TLS-кандидаты через компилятор службы.
- При запуске Zapret2 после большого набора Legacy-проверок воспроизводилась
  ошибка инициализации DLL `0xc0000142`. После переноса Zapret2 в начало набора
  полный прогон прошёл. Причина зависимости от порядка не установлена;
  это не следует считать исправлением запуска рабочего движка.

Семантика параметров сверена с Lua в поставке и
[руководством Zapret2 v1.0.5.2](https://github.com/bol-van/zapret2/blob/v1.0.5.2/docs/manual.md).

## Исправление проверок после прогона 28 сентября

В журнале в 21:49 сбалансированный режим остановился на DNS как для Discord,
так и для контрольных сайтов. Следующий быстрый поиск запустил шесть проверок
кандидатов с тайм-аутами по 3 секунды и был отменён на седьмом кандидате.
Успешный запуск процесса не означает успешный обход.

- Первый системный DNS-запрос теперь продолжает ожидаться при запуске повтора:
  раньше его поздний ответ терялся. Регрессионный тест воспроизводит ответ
  после половины бюджета и до общего дедлайна.
- DNS получает отдельные 10 секунд; успешные ответы сохраняются на сессию.
  Транспорт получает полный бюджет: 5/7/10 секунд для быстрого/баланса/глубокого.
- HTTPS-проверки идут напрямую, без автоматически подхваченного proxy.
- Незавершённый HTTPS-запрос получает `request_timeout`: отсутствие ответа
  само по себе не доказывает ошибку TCP. Локальный тест принимает TCP и
  задерживает TLS, проверяя как результат цели, так и итог серии.
- В журнал подготовки добавлены бюджет запроса и количество раундов.

120 тестов adaptive_strategy прошли, один сетевой диагностический тест
пропущен. Эти изменения исправляют проверку; работоспособность конкретных
стратегий на сети пользователя новым прогоном ещё не подтверждена.
