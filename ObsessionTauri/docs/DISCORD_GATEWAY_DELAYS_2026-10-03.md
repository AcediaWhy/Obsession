# Discord после routes: HTTPS работает, запуск клиента медленный

Пользователь сообщил, что Discord запускается медленно, и предположил, что
ночной конфиг утром перестал работать. Уточнение пользователя: утренний вывод
основан на показаниях второго теста; отдельную фактическую недоступность
Discord он не проверял. Поэтому «конфиг умер за ночь» пока не наблюдение.

## Сравнение ночи и утра

| Замер, местное время Самары | Кандидат: HTTPS | Контроль без обхода: HTTPS | Итог |
| --- | --- | --- | --- |
| 2 октября, 23:50–23:51 | 18/18 | 0/18 | effect_confirmed |
| 3 октября, 10:55–10:56 | 18/18 | 0/18 | effect_confirmed |

В обоих сравнениях один кандидат: `multidisorder:pos=1,midsld`, `out_range=-d10`.
Основные IP закреплены: `discord.com → 162.159.128.233:443`,
`gateway.discord.gg → 162.159.135.234:443`. Scope и resources fingerprints
совпадают. Порядок блоков разный; в каждом три пары, два раунда на блок.
В обоих отчётах все блоки имеют runtime_healthy=true и route_unchanged=true,
несвязанный HTTPS-контроль здоров. Это повторение положительного результата
на проверяемых адресах через 11 часов, а не непрерывное наблюдение всю ночь.
VPN независимой проверкой не подтверждён; header сохраняет это ограничение.

Утром API отвечает за 138–149 мс, HTML + один JS за 241–281 мс,
gateway HTTPS за 250–280 мс. Во всех контрольных запросах без обхода —
тайм-аут около 3 секунд, у основных принадлежащих пробам сокетов на этапе TLS.
Контрольные отказы не означают неработающий кандидат. Финальный статус второго
утреннего теста — effect_confirmed, failureStage=null, исходный конфиг возвращён
и проходит проверку после возврата.

В 10:25 «подбор с нуля» также нашёл этот же кандидат с первой попытки:
три полных раунда пройдены, основной API использовал .138.232, .137.232,
.135.232; gateway .133.234, .130.234, .135.234. Выбор нескольких DNS-адресов
работает. Но исходный конфиг был здоров уже до начала этого теста.

## Найденный вариант и постоянная настройка различаются

Все эти запуски диагностические и возвращают исходную конфигурацию.
`confirmed_candidate` содержит `pos=1,midsld`, а `final_config` после возврата
содержит прежний `pos=1,2,midsld,sniext`. Cache и события применения после
старта также указывают на прежний adaptive-4c7cfc73197b53dd121fba57.
Не считать тест применением нового найденного варианта. Старый профиль тоже
проходит исходные HTTPS-проверки до и после сравнения.

## Что установлено и чего не хватает

HTTPS-эффект подтверждён в двух окнах. Полная утренняя поломка профиля и его
короткий срок жизни не установлены. Медленный реальный Gateway подтверждён.
Существующий тест делает обычный HTTPS GET gateway и проверяет HTML/один JS;
WebSocket upgrade, Gateway HELLO, авторизованный READY и reconnect он не
измеряет. Поэтому быстрый зелёный HTTPS-тест не оценивает задержку клиента.

Клиентский лог не разделяет DNS, TCP, TLS и WebSocket upgrade и не записывает
IP этого сокета. Нельзя выбрать между плохим первым IP, повторной отправкой,
отличием ClientHello Chromium и особенностью Gateway по одному таймеру.
Следующее полезное измерение — этапы реального WSS-подключения и регионального
reconnect, включая адрес/время/receipt исполнения и время до первого ответа.
Нужно учитывать устойчивость и задержку, а также ясно показывать контроль без
обхода и проверяемый вариант. Текущее отображение validating_effect не сообщает
конкретную arm; точная экранная надпись, которую пользователь принял за отказ,
по имеющимся данным не восстановлена.

Исходные отчёты и их SHA-256 перечислены в
`DISCORD_GATEWAY_DELAYS_RECEIPTS_2026-10-03.json`. Код, настройки DNS,
сохранённые конфиги и установленная программа этим разбором не изменены.
