# Неудачный подбор Discord после установки v7

Источник: `measurement-20261001T175405.713447100Z-25172-0.jsonl`,
сеанс 21:54:05–21:55:36 Europe/Samara. Приложение действительно содержит
v7: policy в заголовке отчёта совпадает, SHA256 установленного obsession.exe
равен текущему release binary:
`c8618d09f081788a9112910695ef5334248c79566bdd19ba9612b48283186706`.

## Подтверждённые факты

- Выполнены 12 разных кандидатов: pure reordering, fake, HostFakeSplit,
  clone+ACK+FakeDSplit, FakeDDisorder, двухформный fake+padencap+MultiSplit,
  clone+TTL, clone+padencap+patterned overlap и clone+MD5+FakeDDisorder.
  Геометрической цепочки уточнений в этом сеансе нет.
- Discord API, `/app` и gateway не дали ни одного HTTPS-ответа при кандидатах.
  Один длинный контроль тоже не восстановил доступ. Supplementary TCP
  соединяется за 42–57 мс, TLS к двум основным authorities каждый раз
  достигает двухсекундного тайм-аута.
- Контрольные example.com, Cloudflare и Microsoft отвечали при подготовке.
  Исходный профиль до и после теста Discord не прошёл. Исходная конфигурация
  восстановлена; 13-й кандидат отклонён до запуска: оставалось 2793 мс при
  минимуме 5500 мс. Полный сеанс с возвратом занял 91201 мс.
- После теста пользователь подтвердил, что сам Discord тоже недоступен.
- При чтении сетевого состояния: маршрут через Wi-Fi/192.168.0.1, DNS
  192.168.0.1, активного VPN-адаптера не обнаружено. Это снимок состояния,
  а не доказательство отсутствия любых программных прокси во время теста.
- Независимый Google DNS вернул IP из отчёта для обоих Discord-hostname.
  Системный DNS не изменялся.

## Независимые HTTPS-проверки

Проверки curl/Schannel выполнялись вне сетевых ограничений песочницы,
без proxy, пользовательских токенов, изменения DNS и запуска DPI.
К моменту поздних проверок процессы приложения и winws2 уже отсутствовали.

| Запрос | Результат |
| --- | --- |
| Google generate_204 | HTTP 204, TLS 192 мс |
| www.cloudflare.com, принудительно IP 162.159.137.232 | HTTP 200, TLS 107 мс |
| discord.com API, принудительно тот же IP 162.159.137.232 | TLS не завершился, тайм-аут 4006 мс |

Различие на одном IP совместимо с фильтрацией по TLS SNI. IP как таковой
доступен; проблема не ограничивается Rustls/reqwest. Само сравнение не
устанавливает конкретное оборудование, провайдера или правило фильтрации.

## Существенный диагностический пробел

В `runtime-service/src/dpi_executor.rs` readiness проверяет, что процесс
не завершился за ограниченное время. Это не подтверждает открытие capture,
совпадение профиля, вызов конкретной Lua-функции или успешную отправку
изменённых сегментов. В отчётах это честно отмечено `packet_effect=not_measured`.

CreateProcess использует CREATE_NO_WINDOW и обычный STARTUPINFOW без
перенаправления stdout/stderr. В argv compiler нет включённого engine debug
log. Поэтому ошибки обработки пакета после старта в app.log не попадают.
Существующие журналы не позволяют отличить стратегию без эффекта от стратегии,
которая не была применена к ClientHello. Признаков срыва materialization,
generation collision или failed start в этом сеансе нет.

Проверка compiler не выявила пропущенные Lua или списки: zapret-lib загружается
перед zapret-antidpi, adaptive профиль получает защищённый discord.txt,
gateway.discord.gg входит в scope через discord.gg. Отсутствие hostlist
в записи pack не означает отсутствие фильтра: compiler подставляет список
категории. Это не заменяет наблюдение реального совпадения профиля.

Следующая проверка должна фиксировать capture → profile match → Lua call →
send result/ответ сервера в коротком ограниченном сеансе. Увеличение количества
кандидатов не отвечает на этот вопрос. До такого измерения точная причина
неработоспособности стратегий и предел реализуемости не установлены.
