# План: турнир профилей и сборщик конфигураций Zapret2

Дата: 4 октября 2026 года. Статус: реализованы каталог, области отдельных действий, конечный турнир сетевых проб, защищённое применение, направленные прикладные испытания и архив. Приёмка на сети провайдера, контроль общих сетевых сбоев, атрибуция исполнения и сборщик ещё не завершены. [Первый шаг](ZAPRET2_IMPLEMENTATION_CHECKPOINT_2026-10-04.md), [второй шаг](ZAPRET2_TOURNAMENT_CHECKPOINT_2026-10-04.md), [прикладные испытания, история и диагностические факты](ZAPRET2_SCENARIOS_CHECKPOINT_2026-10-04.md).

Основа исследования: [каталог кандидатов](ZAPRET2_CANDIDATE_RESEARCH_2026-10-04.md). Исторические документы adaptive_strategy описывают прежние эксперименты и не считаются перечнем действующих возможностей.

## Цель и границы первой версии

По запросу пользователя находить и подтверждать конфигурацию для конкретного сценария Discord или YouTube. Использовать ограниченный каталог известных кандидатов; сохранять результаты по отдельным функциям; собирать совместимые части, если ни один цельный профиль не покрывает сценарий.

Первый полезный выпуск — турнир фиксированных профилей с достоверными результатами. Сборщик добавляется после подтверждения, что частичные успехи существуют и их можно разделить фильтрами движка. Полноценная фоновая автоматическая смена, открытый генератор Lua и возвращение старого adaptive_strategy не входят в первую версию.

Gaming остаётся на существующем управлении до появления собственного измеримого сценария. Голос Discord получает отдельный статус; до проверки настоящего вызова он не может быть объявлен рабочим. Существующие ручные профили сохраняются. Очистка постороннего бойлерплейта — отдельная работа, кроме кода, непосредственно заменённого новой реализацией.

## Основные решения

- Исходный runtime — точка возврата, а не гарантированно рабочий эталон. Поиск допустим без единого рабочего кандидата.
- У каждого кандидата фиксированная идентичность: действия и их порядок, области исполнения, filters, ranges, ресурсы с хешами, версия движка и пакета. Названия и номера уровней не определяют эквивалентность.
- Сообщение автора, успешный blockcheck, локальная совместимость и подтверждённый сценарий хранятся раздельно. Чужой успех помогает выбрать порядок, но не проходит испытание за пользователя.
- В runtime передаются разрешённые ID профилей, областей и сборок. UI и сетевые источники не передают исполняемый Lua, пути или произвольные аргументы привилегированной службе.
- Сетевые испытания кандидатов сериализованы. Параллельность возможна только для совместимых проб внутри одного неизменного runtime с ограниченной нагрузкой.
- Ошибки запуска, неопределённое исполнение, неготовая тестовая цель и общие сетевые сбои не являются отрицательным результатом механизма обхода.
- Сборка получает собственный результат: успех частей по отдельности не доказывает успех их сочетания.
- Подбор завершается точным возвратом исходного состояния. Постоянное применение — отдельное действие с проверкой актуальности результата. Возврат неработавших исходных настроек не называется восстановлением доступа.

## Этап 0. Зафиксировать исходное поведение и критерии

Работы:

1. Описать текущие команды выбора, запуска, подбора, отмены и применения; проверить фактический путь через службу.
2. Зафиксировать исходный DpiStartRequest, runtime generation, выбор профилей и версию настроек. Если точный запрос активной сессии неизвестен, сохранить существующий отказ от угадывания.
3. Определить пользовательские сценарии первой версии: запуск/подключение Discord и просмотр публичного видео YouTube. Для каждого перечислить обязательные и диагностические проверки.
4. Подготовить сопоставление с нынешним подбором: одинаковые кандидаты и цели там, где это возможно. Метрики — подтверждённые сценарии, ложные успехи, число замен runtime, время и трафик испытания.

Результат: краткий контракт поведения и воспроизводимый протокол сравнения. Исходная сеть может быть неисправна; это отдельное условие опыта.

Условие завершения: для каждого статуса понятно, какие факты разрешают его показать; возврат, отмена и применение имеют явные владельцев и границы.

## Этап 1. Подготовить каталог кандидатов

Работы:

1. Разобрать существующие 19 стандартных правил, 32 пресета и эксперимент; группировать по механизму и области применения, исключить точные дубли в рамках одной задачи. Различия payload, диапазонов, ресурсов и фильтров не терять.
2. Оформить C01–C08 из исследования как независимые карточки: источник и дата, полный исходный контекст, выделенная часть, собственные изменения, заявленный результат, известные отказы, необходимые ресурсы, неизвестные условия.
3. Первая волна: существующие контрольные профили, C01/C02, C03, C04/C07, C05. C06 требует более сложного сохранения стадий; C08 — дополнительная точка QUIC-параметра. Это приоритет допуска, а не обещание проверить всё за один запуск.
4. Для каждого кандидата проверить наличие функций/параметров в закреплённом движке и bundled Lua. Сверить содержимое blobs; замена внешнего blob локальным создаёт производного кандидата.
5. Перенос Legacy добавлять точечно, с описанием семантических различий, включая исходную сегментацию ClientHello. Старые сохранённые результаты не выдавать за свежее подтверждение.

Результат: версионированный каталог исследовательского пакета с небольшим набором разнообразных основ. Не импортировать чужие батники и автопереключатели целиком.

Условие завершения: каждый допущенный кандидат воспроизводим, его происхождение и отличия известны; отсутствующие ресурсы и неподдерживаемые возможности блокируют допуск.

## Этап 2. Сохранить семантику исполнения и проверить локально

Работы:

1. Расширить представление фиксированного профиля настолько, насколько нужно кандидатам: отдельные области payload/direction/range для действий вместо предположения, что все действия имеют один фильтр. Не создавать язык произвольных программ.
2. Разобрать случай C02: wssize до переключения payload и multidisorder после него. Учитывать, что hostlist/L7-фильтр может не позволить выбрать профиль до распознавания ClientHello. Одного порядка строк недостаточно для доказательства нужного воздействия.
3. Синхронизировать проверку и сборку профилей в приложении и службе; явно версионировать изменение схемы и совместимость пакета. Сохранить запуск прежних профилей с прежним смыслом.
4. Проверить новые профили настоящим CLI parser в dry-run. Ошибки не маскировать повторными запусками.
5. На локальном стенде проверить полный TLS и прикладной обмен для малого и многосегментного ClientHello, повторных отправок и подходящих семейств IP. Проверить сохранность настоящего потока и ограниченность fake/repeats.
6. Для каждого замера получить подтверждение, что нужный профиль и действия исполнялись на соответствующем свежем потоке; если атрибуция недоступна, оставить неопределённость.

Результат: пригодные для управляемого испытания кандидаты и диагностические данные об исполнении. Локальная совместимость не означает обход DPI.

Условие завершения: нет известных нарушений TLS/передачи данных на стенде; нет молчаливо неисполняемых действий; есть проверяемый путь запуска и возврата через службу.

## Этап 3. Сделать измерения полезными для турнира и сборщика

Модель результата отдельной пробы:

- идентификатор запуска, кандидата/сборки, области и runtime generation;
- контекст сети, версия тестера, клиент/транспорт/IP family, цель и фактический адрес;
- исполнение стратегии: подтверждено, не сопоставлено, не применялось;
- результат: passed, failed, inconclusive, not_tested, cancelled;
- этап отказа, время, объём данных, разрешённые технические детали ошибки;
- предел доказательства: handshake, прикладная проба либо реальный сценарий.

Работы:

1. Сохранить быстрые HTTPS-проверки как отсев; раздельно записывать API, Gateway, CDN и updater. Успех REST /gateway не заменяет WSS-сессию Gateway.
2. Добавить проверку доступного без пользовательского токена этапа Gateway WSS с точным обозначением её границы. Полноценная готовность пользовательского Discord подтверждается самим клиентом или явно пользователем; пассивный TLS-трафик этого не доказывает.
3. Для YouTube разделить сайт, картинки и медиаданные. Финалисты проходят сценарий публичного видео через браузерный адаптер либо направленное ручное испытание. Учесть протухание URL, ошибки контента и фактический транспорт; успешный fallback на TCP не подтверждает QUIC.
4. Расширение QUIC до прикладного HTTP/3 тестировать отдельно. Пока доступен только handshake, соответствующий результат не претендует на подтверждение видео.
5. Применять свежие соединения и управляемые сессии тестера, чтобы старый пул, TLS resumption, кеш или живой WSS не приписали новому кандидату чужую работу. Холодное и повторное подключение — разные сценарии.
6. Проверять окружение и пригодность целей, сохраняя результаты проверок отдельно от стратегии. Смена сети делает текущий раунд несопоставимым. Неготовая цель не ухудшает рейтинг всех профилей.
7. Для раннего отсева цельного профиля разрешить завершение после обязательного отказа; перед исключением как источника частей сохранить/дособрать остальные нужные проверки в пределах бюджета. Не превращать неиспытанные функции в неработающие.

Результат: матрица «кандидат × функция × условия» с явными неизвестными значениями.

Условие завершения: интерфейс и алгоритм не могут повысить handshake до успешного приложения; один и тот же записанный результат детерминированно приводит к одной оценке.

## Этап 4. Реализовать турнир фиксированных профилей

Последовательность:

1. Измерить исходный профиль, если он пригоден для испытания. Он может проиграть все проверки. Контроль без обхода предусмотреть как отдельный явный режим диагностики, а не незаметное отключение работающего соединения.
2. Сформировать ограниченный список различных семейств с учётом совместимости. До начала объявить бюджет времени, трафика и максимальное число замен runtime.
3. Быстро проверить основы. Отдельно сохранить кандидатов с частичным покрытием.
4. Выделить 2–3 финалиста, если столько пригодных есть. При одном — подтверждать его повторяемость, при нуле — перейти к анализу пробелов.
5. Провести несколько раундов с чередованием порядка кандидатов и контрольными измерениями. Использовать свежие потоки, сопоставимые цели и учитывать изменения DNS/CDN/сети. Новый порт и повторный запуск не гарантируют сброс состояния на стороне DPI.
6. Ранжировать сначала по выполнению обязательного сценария, затем по наблюдаемой повторяемости, задержкам и стоимости. Числовые веса не выдавать за вероятность успеха. При малой выборке разрешить ничью и недостаточность данных.
7. Зарезервировать бюджет на возврат перед каждой новой попыткой. Если времени осталось мало, закончить с имеющимися доказательствами; не сокращать обязательное подтверждение до одного случайного успеха.
8. Вернуть исходный runtime и выдать результат для отдельного применения.

Предлагаемая семантика режимов:

| Режим | Задача |
| --- | --- |
| Быстро | Найти и кратко перепроверить пригодный вариант; честно показать ограниченность проверки |
| Баланс | Сравнить несколько финалистов и проверить основной сценарий |
| Глубоко | Расширить повторные сценарии и исследовать резерв; долгую выдержку показывать отдельно |

Точные лимиты и число раундов зафиксировать после замеров стоимости запуска и проб. Существующие 90/180/300 секунд использовать как исходный ориентир UX, а не гарантию полного турнира в любой сети.

Условие завершения: на воспроизводимых искусственных сбоях турнир не выбирает одноразовый успех вместо устойчивого результата; на реальной сети есть сравнение с нынешним первым прошедшим профилем. Отсутствие выигрыша фиксируется как результат, а не компенсируется новыми эвристиками без основания.

## Этап 5. Добавить сборщик совместимых частей

Работы:

1. Определить фиксированные различимые области: например, группы API/Gateway/CDN Discord и сайт/медиадомены YouTube. Привязку строить по реальным фильтрам движка, не по произвольным пользовательским названиям.
2. Проверить hostlists, поддомены, исключения, IP family, L7, порты и порядок первого совпадения. Для пересекающихся областей требовать общий профиль либо отклонять сочетание. Один неразличимый зашифрованный поток нельзя разделить между правилами по смыслу запросов.
3. Для каждой обязательной области выбрать до двух прошедших кандидатов. При пробеле не строить десятки комбинаций остальных областей — направить оставшийся бюджет на пробел.
4. Сначала построить одну компактную сборку, при необходимости несколько альтернатив с заранее ограниченным числом, например до четырёх. Значение уточнить по длительности испытаний.
5. Компилировать только разрешённые ID областей и профилей. Служба повторно проверяет разрешённость и совместимость композиции.
6. Испытать сборку целиком: исходный проблемный сценарий и ранее работавшие функции. Сборки соревнуются на том же механизме турнира, а не получают автоматический успех из суммы частей.
7. Отказ сочетания хранить отдельно от результатов его компонентов. Для разбирательства возвращать одну часть за шаг в пределах бюджета.

Условие допуска этапа: обнаружены воспроизводимые дополняющие друг друга частичные успехи и технически различимые области. Если их нет, самостоятельный турнир остаётся полезным результатом, сборщик не расширять искусственно.

Условие завершения: есть демонстрация случая, где отдельные профили не покрывают сценарий, а проверенная сборка покрывает, и демонстрация корректного отказа при конфликтующих правилах.

## Этап 6. Применение, память и интерфейс

Работы:

1. Сохранить существующие карточки и ручной выбор. Добавить понятные фазы подготовки, отсева, сравнения, проверки сборки и возврата; показывать число выполненных испытаний и затраченный бюджет.
2. Показывать основной результат, покрытие функций и границы доказательств. Различать «подключение подтверждено», «сценарий подтверждён», «частичный результат», «не проверено» и «не удалось оценить».
3. Связать кнопку применения с точным результатом, контекстом и текущими настройками. При изменении сети, версии пакета или выбора требовать свежую проверку; не применять устаревшую рекомендацию молча.
4. Постоянное применение выполнять транзакционно: при сбое проверки/сохранения вернуть точный предыдущий набор. При ошибке возврата показать отдельное состояние и прекратить подбор.
5. Хранить ограниченную историю измерений с версиями и сроком актуальности. История влияет на порядок испытаний, но не заменяет свежую проверку. Не сохранять токены, содержимое трафика и подписанные медиассылки как постоянную историю.
6. Резерв назначать только при наличии собственных подтверждений. Несовпадение провалов оценивать лишь при достаточных сопоставимых наблюдениях; различное название семейства не доказывает независимости. В первой версии резерв применяется вручную.

Условие завершения: отмена, закрытие UI, изменение настроек и повторное нажатие не оставляют тестовый runtime под видом постоянного; пользователь видит фактический текущий статус даже после сбоя возврата.

## Этап 7. Ограниченная оптимизация после полезного результата

Добавлять после работающего турнира, измерений и проверки сборщика:

- небольшое число фиксированных вариантов повторов, позиций и состава действий;
- привязка каждой производной к родителю и гипотезе;
- сравнение стоимости и устойчивости с родителем;
- повторная проверка на сценариях/целях, не участвовавших в настройке;
- прекращение ветки по бюджету или отсутствию полезного сигнала.

Новая механика обхода исследуется отдельно, если каталог не даёт покрытия. При одинаковых неинформативных провалах увеличение числа параметров не считается прогрессом. Автовосстановление на основе основного/резервного набора — последующий отдельный проект после накопления достоверных данных.

## Обязательное поведение при неудачах

| Ситуация | Результат |
| --- | --- |
| Все кандидаты провалили всё при пригодных измерениях | Рабочий вариант не найден; сохранить причины и вернуть исходное состояние |
| У всех не проходит CDN | Явный пробел CDN; искать его кандидатов, не заявлять сборку успешной |
| Сеть/тестовая цель неисправны | Испытание не оценивает стратегию; приостановить/завершить раунд без отрицательного рейтинга |
| Правило не применилось или исполнение неизвестно | Ошибка допуска/атрибуции; не считать эксперимент проверкой нужного механизма |
| Части работали, сборка нет | Отклонить сборку; проверить конфликт, не дискредитировать части автоматически |
| Исходный профиль уже не работал | Вернуть настройки, отдельно сообщить, что доступ не подтверждён |
| Отмена или закрытие окна | Завершить принадлежащую операции очистку и возврат |
| Смена сети/ручного выбора | Не применять решение старого контекста; завершить принадлежащую операции транзакцию |
| Возврат runtime не подтверждён | Прекратить поиск; показать ошибку, не останавливать неизвестное поколение по догадке |
| Бюджет закончился | Вернуть исходное состояние, сохранить частичные факты; не объявлять неполный тест успешным |

## Проверки реализации и выпуск

Целевые проверки добавлять по мере изменения соответствующих модулей:

- семантика стадий и порядка профилей, конфликты областей, воспроизводимость сборки;
- неправильные ресурсы/версии, фактическое исполнение, полный TLS и прикладной обмен на стенде;
- ложный однократный успех, неопределённые результаты, смена сети и истечение бюджета;
- частичное покрытие и неразличимые области, противоречия измерений;
- отмена при запуске/измерении/возврате, смена runtime generation, ошибка сохранения, повторный сбой возврата;
- UI: отсутствие ложного зелёного статуса, актуальность применения, ручной выбор и восстановление состояния после перезапуска.

Использовать существующие проверки проекта по изменённым областям: Rust-тесты приложения/службы/протокола, Vitest, `npm run build`, `npm run audit:dpi`, `npm run test:dpi-configs`, `npm run verify:dpi-parsers`. Команды перечислены для будущей реализации; при написании этого плана они не запускались.

Реальные сетевые испытания проводить как отдельный явно запущенный этап с видимым влиянием на соединения. Для сравнения фиксировать ОС/клиент/движок/сеть, порядок опытов, конечный сценарий и наблюдаемую стабильность. Результаты одной сети не экстраполировать на всех провайдеров. Если доступен только один стенд, выпуск маркировать как экспериментальный в пределах этой проверки.

Сначала внутренний исследовательский пакет, затем опциональный турнир, затем сборщик при выполнении его условия допуска. Установка релиза и включение функции не происходят как побочный эффект подготовки исходников.

## Порядок поставки

1. Каталог и точная совместимость кандидатов: этапы 0–2.
2. Измерения и полезный самостоятельный турнир: этапы 3–4 плюс минимальный UI/применение из этапа 6.
3. Сборщик на подтверждённых частичных результатах: этап 5 и расширение UI/истории из этапа 6.
4. Ограниченная оптимизация: этап 7, только после измеренного результата предыдущих этапов.

Первая контрольная точка: небольшой набор новых кандидатов корректно исполняется, измеряется по функциям и позволяет объяснить свой результат. До этого не расширять систему рейтингов и генерации.
