## Что теперь подтверждено

Второй отчёт содержит sampling policy `repeatability_full_block_sampling_v2`.
Все шесть блоков имеют два реально измеренных раунда и разные generations.
Порядок: candidate/control, control/candidate, candidate/control.
DNS и несвязанные HTTPS контроли здоровы, движок жив, маршруты неизменны.
Полное сравнение заняло 35830 мс; весь тест — 51691 мс. Найденный кандидат
подтвердился за 14697 мс. Прежняя ошибка ранней остановки контроля устранена
и проверена на пользовательской сети.

При включённом кандидате API Discord возвращал проверенный JSON,
страница /app — HTML и один JavaScript asset, gateway — HTTPS ответ.
Без обхода каждый endpoint во всех контрольных раундах истекал примерно
через три секунды. Пакетное наблюдение дополнительных TLS сокетов согласуется
с этим: в контроле ClientHello без ACK progress/ServerHello, с кандидатом
ACK продвигается, приходит ServerHello и входящие TLS данные.
Это подтверждает эффект обхода в данном коротком окне проверки.

## Что остаётся необъяснённым

За 17 минут до успешного теста первый кандидат и ещё десять не работали.
В 11 коротких экранах было 33 неуспешных endpoint checks; дополнительная
проверка одного кандидата с ожиданием около семи секунд тоже дала три отказа.
TCP в отдельных диагностических соединениях устанавливался за 44–71 мс,
а TLS истекал около двух секунд. Наблюдались ClientHello, повторные seq,
ACK progress 0 и отсутствие входящего TLS ответа.

Наблюдатель был active без queue drops, parse errors, evictions и sensor
failure. В сохранённых ограниченных Lua trace windows есть вызовы нужного
профиля и успешные send API results. Эти результаты не удостоверяют доставку
пакета на физическую сеть и не исключают отсутствующие события за пределами
усечённого окна. Явного service startup failure здесь нет.

Discord IP изменился с `162.159.138.232` на `162.159.137.232`, но gateway
в обоих тестах использовал `162.159.133.234` и тоже перешёл от TLS timeout
к TLS success. Поэтому смена адреса Discord сама по себе не установлена
как причина общего перехода.

Особенно существенно, что во втором тесте исходный конфиг работал уже
**до начала подбора**. Система доказала эффект bypass относительно
passthrough в этот момент; она не доказала, что её выбор устранил сетевое
состояние из первого теста. Оба запуска cold, history_enabled=false;
причина выбора первого кандидата одинакова. Межсессионное обучение этим
успехом не демонстрируется. Planner остаётся эвристическим.

Следующее содержательное измерение должно разделить время, IP и конфиг:
проверять исходный вариант, тот же кандидат и passthrough на одинаковых
закреплённых адресах в успешном и неуспешном состоянии. Повтор текущего
теста с новой DNS подготовкой смешивает время и адрес. Причина колебаний
пока не установлена, новый код planner по этим данным не менялся.
WSS, выполнение страницы в браузере, голос и длительная доступность
этим HTTPS протоколом не измерены.
