# Adaptive Zapret2 Strategy Brain Design

## 1. Контекст

Obsession уже умеет вручную переключаться между Zapret Legacy и Zapret2 Beta,
проверяет целостность бинарников и Strategy Pack, не запускает два DPI-движка
одновременно и возвращается к последнему подтверждённому Legacy-набору после
сбоя Zapret2.

Встроенный pack `builtin.base 0.2.3` прошёл live-проверку:

- Discord открывается и отправляет текстовые сообщения;
- YouTube открывается;
- 4K-видео быстро загружается и продолжает воспроизведение после перемотки;
- рабочий YouTube TLS-профиль использует
  `multidisorder_legacy:pos=1,midsld`.

Ручная диагностика показала ценность Zapret2: движок корректно распознавал SNI,
hostlist и профиль, но обычный `multidisorder` иначе обрабатывал reassembled
ClientHello. Замена одной функции Strategy Pack на `multidisorder_legacy`
восстановила доступ без изменения `winws2.exe`.

Следующий этап — дать Мозгу возможность локально создавать и проверять новые
безопасные комбинации Strategy Pack, не исполняя произвольный сгенерированный
Lua-код.

## 2. Цель

Создать локальный контролируемый recovery-контур для YouTube и Discord:

1. Мозг пассивно обнаруживает устойчивую блокировку.
2. Пользователь получает предложение запустить поиск.
3. После подтверждения Мозг последовательно проверяет ограниченный набор
   безопасных кандидатов.
4. Найденный кандидат включается на 60 секунд для ручной проверки.
5. Пользователь подтверждает применение или продолжает поиск.
6. Подтверждённая стратегия сохраняется для текущего отпечатка сети и затем
   применяется на этой сети автоматически.

## 3. Не цели MVP

- генерация и исполнение произвольного Lua;
- использование облачного API или LLM;
- автоматический запуск поиска без подтверждения пользователя;
- автоматическое постоянное применение нового кандидата;
- поддержка категорий кроме YouTube и Discord;
- одновременный запуск Legacy и Zapret2 на пересекающемся трафике;
- изменение системного `hosts`;
- автоматическая отправка сообщений от имени пользователя в Discord.

## 4. Режим взаимодействия

Используется гибридная модель.

### 4.1 Пассивное обнаружение

Наблюдатель продолжает собирать сетевые сигналы без переключения стратегии.
Один reset или timeout не считается блокировкой. Предложение recovery
показывается только при устойчивом сочетании сигналов в ограниченном окне:

- TLS reset или blackhole;
- отсутствие ServerHello после повторных попыток;
- повторные retransmit/timeout;
- контрольные адреса вне проблемной категории остаются доступны;
- активная стратегия ранее считалась рабочей.

### 4.2 Предложение поиска

UI показывает уведомление вида:

> YouTube, вероятно, заблокирован. Запустить поиск стратегии?

Поиск начинается только после нажатия `Найти стратегию`.

### 4.3 Поиск

- одновременно проверяется один кандидат;
- одновременно восстанавливается одна категория;
- лимит — до 12 кандидатов за одну recovery-сессию;
- тестовое окно кандидата — не более 10–15 секунд;
- очевидный успех или провал завершает окно досрочно;
- поиск можно отменить в любой момент;
- между recovery-сессиями действует cooldown;
- после неудачного кандидата восстанавливается last-known-good runtime.

Кандидат целевой категории меняется, а подтверждённый профиль второй категории
остаётся в том же invocation. Перезапуск единственного процесса `winws2.exe`
может вызвать краткое переподключение второй категории; UI предупреждает об
этом до начала поиска.

### 4.4 Временная ручная проверка

После автоматического успеха кандидат остаётся активным не более 60 секунд.
UI показывает:

- результаты автоматических probes;
- оставшееся время;
- `Работает — сохранить`;
- `Не работает — продолжить поиск`;
- `Отмена и возврат`.

Если пользователь ничего не выбрал, включается предыдущая подтверждённая
стратегия. Новый кандидат не становится постоянным автоматически.

## 5. Архитектура

### 5.1 Safe Strategy DSL

Мозг создаёт не Lua-код, а типизированное описание из разрешённых примитивов.
Пример:

```json
{
  "category": "youtube_twitch",
  "transport": "tls",
  "function": "multidisorder_legacy",
  "position": ["1", "midsld"],
  "payload": ["tls_client_hello"],
  "out_range": "-d10"
}
```

DSL разрешает только заранее проверенные:

- Lua-функции из bundled `zapret-antidpi.lua`;
- payload и L7-фильтры;
- position markers;
- fake blobs;
- bounded repeats;
- bounded TCP sequence/timestamp/TTL options;
- безопасные диапазоны обработки.

DSL запрещает произвольные Lua-строки, пути, команды, загрузку файлов,
неизвестные функции и параметры вне допустимых границ.

### 5.2 Strategy Validator

Перед запуском кандидат проходит отдельный валидатор:

- категория — только `youtube_twitch` или `discord`;
- функция и каждый аргумент входят в allowlist;
- hostlist задаётся приложением, а не генератором;
- capture ограничен необходимыми TCP/UDP-портами;
- число функций, repeats и диапазоны ограничены;
- bundled Lua/blob проходят существующую проверку SHA-256;
- кандидат не может отключить lifecycle, fallback или generation checks.

### 5.3 Deterministic Candidate Generator

Генератор полностью локальный и не использует модель машинного обучения.
Порядок кандидатов определяется диагнозом и накопленной статистикой:

1. подтверждённая стратегия этой сети;
2. встроенные known-good стратегии;
3. близкие безопасные мутации параметров;
4. более агрессивные allowlisted комбинации.

Генератор меняет минимальное число параметров за шаг. Для TLS и QUIC ведутся
раздельные линии кандидатов. Discord и YouTube не смешиваются в одном поиске.

### 5.4 Recovery Coordinator

Координатор реализует state machine:

```text
Idle
  -> Suggested
  -> Searching
  -> CandidateProbe
  -> TemporaryVerification
  -> AwaitingApproval
  -> Applied | ContinueSearch | RolledBack | Exhausted | Cancelled
```

Все переходы generation-safe. Stale task не может остановить или подтвердить
новый runtime. Shutdown и ручной Stop всегда имеют приоритет.

### 5.5 Candidate Compiler

Валидный DSL компилируется в существующие `StrategyDef`, `Zapret2Profile` и
`Zapret2Invocation`. Используются только bundled Lua-функции и blobs. На первом
этапе кандидаты могут существовать только в памяти; подтверждённый результат
записывается как нормализованный JSON DSL, а не как Lua.

### 5.6 Probe Evaluator

Автоматическая оценка объединяет активные probes и сигналы Наблюдателя.

Для YouTube:

- DNS и TCP/443;
- TLS ServerHello для `youtube.com`/`www.youtube.com`;
- успешный HTTPS-ответ страницы;
- отсутствие reset/blackhole в окне;
- при ручной проверке — успешные соединения `googlevideo.com`.

Для Discord:

- TLS ServerHello для `discord.com` и `gateway.discord.gg`;
- успешный HTTPS-ответ;
- возможность установить gateway/WebSocket-соединение без использования
  пользовательского токена;
- отсутствие reset/blackhole в окне;
- фактическую отправку сообщения подтверждает пользователь.

Успех требует нескольких независимых положительных сигналов. Один HTTP-ответ
или один ServerHello недостаточен для постоянного применения.

### 5.7 Network Strategy Cache

Подтверждённый DSL хранится по ключу:

```text
network_fingerprint + category + engine_version + strategy_schema_version
```

Отпечаток использует уже доступные безопасные признаки сети: интерфейс,
шлюз/MAC, ASN/провайдер и регион при наличии. Секреты, SSID в открытом виде и
пользовательский трафик в cache не записываются.

После ручного подтверждения стратегия автоматически применяется при следующем
подключении к той же сети. Ошибка probes после запуска вызывает rollback и
снижает рейтинг cache entry. Другая сеть получает независимый результат.

### 5.8 UI

Существующий DPI-экран получает:

- уведомление о вероятной блокировке;
- кнопку `Найти стратегию`;
- предупреждение о кратких переподключениях;
- прогресс `кандидат N из 12`;
- текущий этап и результаты probes;
- кнопку отмены;
- 60-секундную карточку ручной проверки;
- `Работает — сохранить` и `Не работает — продолжить поиск`;
- просмотр подтверждённой стратегии и кнопку её сброса для текущей сети.

## 6. Ресурсные ограничения

- поиск не работает постоянно в фоне;
- генерация DSL не использует GPU и почти не расходует CPU;
- тяжёлые операции выполняются только после ручного запуска;
- кандидаты проверяются последовательно;
- packet capture фильтруется по payload и категории настолько рано, насколько
  позволяет WinDivert/winws2;
- поиск может приостанавливаться при высокой системной нагрузке или работе от
  батареи;
- после отмены не остаются test runtime, timers или временные cache entries.

## 7. Безопасность и rollback

- произвольный сгенерированный Lua запрещён;
- raw DSL из UI не принимается;
- валидатор работает и на backend boundary;
- перед recovery сохраняется точный last-known-good selection;
- только один DPI runtime владеет трафиком;
- неудачный spawn, crash, timeout, cancel и отсутствие подтверждения возвращают
  last-known-good;
- подтверждение относится к конкретным session id, candidate id и generation;
- stale UI event не может применить другой кандидат;
- все решения и причины rollback журналируются без packet payload.

## 8. Проверка MVP

### Автоматические тесты

- DSL parsing/normalization;
- allowlist и граничные значения;
- deterministic candidate ordering;
- лимит 12 кандидатов;
- timeout, cancel и cooldown;
- generation-safe state transitions;
- exact rollback;
- cache isolation между сетями;
- cache version migration;
- подтверждение только текущего candidate/session;
- отсутствие raw Lua/путей в скомпилированном кандидате.

### Live acceptance

1. Создать контролируемый нерабочий YouTube-профиль.
2. Наблюдатель предлагает recovery, но не запускает его сам.
3. Пользователь запускает поиск.
4. Мозг находит рабочий TLS/QUIC-кандидат в пределах бюджета.
5. Кандидат проходит автоматические probes.
6. Пользователь проверяет YouTube в течение временного окна и сохраняет его.
7. После перезапуска на той же сети профиль применяется автоматически.
8. На другой сети cache entry не используется.
9. Отказ, timeout и отмена возвращают точный last-known-good.
10. Аналогичный сценарий проходит для Discord; отправку сообщения подтверждает
    пользователь.

## 9. Порядок реализации

Реализация разбивается на независимые этапы:

1. DSL и validator без runtime-переключений.
2. Generator и deterministic ranking.
3. Recovery state machine и exact rollback.
4. Probe evaluator для YouTube/Discord.
5. Network Strategy Cache.
6. UI поиска и временного подтверждения.
7. Интеграционные тесты и live acceptance.

Каждый этап должен завершаться собственными тестами и отдельным коммитом. До
прохождения live acceptance функция остаётся выключенной feature flag и не
влияет на обычный Legacy/Zapret2 runtime.
